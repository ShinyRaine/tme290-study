§1 · The four computing platforms of a robot (★all 4 missed in June, L2)

Principle: robot hardware sits on a spectrum from "more hardware-like" to "more software-like". The closer to hardware and the more rigid the structure → the faster, the more power-efficient, and the more it can guarantee on-time (real-time) execution — but the less it can do and the harder it is to change. The closer to software, the more flexible → it can do more and is easier to change, but on-time execution becomes harder to guarantee. From hard to soft: PLD/FPGA → microcontroller → CPU → GPU.

What each of the four actually is (following the L2 slides):

· PLD/FPGA (programmable logic device): its function is added in a flashing process — and what the flashing changes is the actual hardware circuitry inside the chip. It is not "installing a program"; it is rewiring the circuit itself (the commonly misunderstood point). Supports inputs/outputs and program loops. Benefit: extremely fast, extremely low-power execution (the signal passes straight through hardware circuitry). Drawback: strong limitations in what features and how much "program" it can hold.

· Microcontroller: also programmed by flashing — but what is flashed is a program: it is written into read-only memory (ROM) and starts executing automatically the moment the device powers on, with no operating system anywhere. Despite its size it supports fairly advanced programs and hardware peripherals (e.g. WiFi, disk storage). Benefit: a simple, low-power, flexible real-time system with outstanding hardware-integration capabilities (it drives motor and sensor pins directly). Drawback: limited program features and execution flexibility.
— What real-time means: a guarantee that execution completes within a set deadline, at predictable times. A microcontroller is real-time precisely because there is no OS to interrupt it. (Remember: real-time = on time and predictable — it has nothing to do with "being fast".)

· CPU: its runtime is managed by an operating system (i.e. a "normal computer", e.g. the Linux kernel); multiple programs run in parallel, memory (RAM) and disk storage interact constantly, and any software and tooling is supported. Benefit: runs advanced software and is relatively quick. Drawback: not capable of real-time operation (when your program gets its turn is decided by the OS scheduler), and therefore a bit limited when interacting with hardware.

· GPU: an execution model similar to a microcontroller, but designed for matrix operations (originally built for graphics — an image is a matrix), with standardized features (e.g. Vulkan); it needs a parallel CPU for memory management and control. Benefit: very high performance for matrix operations → computer vision (CV) and deep neural networks (DNN). Drawback: the CPU–GPU interface complicates low-level implementations.

The course mainly uses CPU-based systems (your computer + the Raspberry Pi).

§2 · Sensors & cameras (L5)

Distance sensors (the two actually on the Kiwi, L4): both are active sensors — they emit a signal themselves and compute distance from the reflection they receive.
· Ultrasonic, the course uses the Devantech SRF08: emits 40 kHz sound pulses and listens for the echo; range 3 cm – 6 m; has a built-in microprocessor and an I²C bus interface.
· Infrared (IR), the course uses the Sharp GP2Y0A41SK0F: emits infrared light and receives the reflection; range only 4 – 30 cm; output is an analogue voltage whose relation to distance is non-linear (a conversion is needed to obtain a distance reading).
Two exam points follow directly: ① both have a minimum range larger than zero (they cannot measure at zero distance — the echo/reflection geometry breaks down when too close); ② ultrasonic (metres) has a far longer range than IR (centimetres).

The camera imaging chain (L5): the image sensor is the central part of any camera (only a handful of manufacturers worldwide); a camera = the interface between the sensor chip and the user. Sensors come as single-channel (mono) or RGB. Colour works like this: a sensor pixel only measures light intensity and cannot tell colours apart, so each pixel is covered by a red/green/blue filter arranged in a Bayer pattern — each 2×2 block has 2 green, 1 red, 1 blue (the human eye is most sensitive to green; the green channel carries the luminance detail, so green gets a double share). Pixel depth is 8/10/12 bits. The raw "Bayer image" from the sensor is not yet a photo — it goes through ISP (image signal processing): demosaicing (Bayer single layer → RGB three channels), white balancing, gamma correction (compensates the eye's non-linear perception), tone mapping, noise reduction. Almost all vision algorithms and ML/AI tools use post-ISP data.

How the two shutters actually work (the slides only name the contrast; the mechanism is):
· Rolling shutter: pixels are exposed and read out row by row — within one frame, each row records the world at a slightly different moment. Benefit: no extra circuitry per pixel, so the sensor is cheap and readout is fast (high frame rates). Cost: with fast-moving subjects the rows are misaligned — skewed, wobbling images (the "jello effect").
· Global shutter: all pixels start and stop exposure at the same instant; the result is first stored in a per-pixel storage cell and then read out together. No motion distortion at all; but each pixel needs an extra storage circuit → more expensive, and readout is usually slower.
One-liner for the exam: rolling = fast + cheap + distorts motion; global = same instant + expensive + slow.

Calibration (the precise L5 definitions — stop remembering these vaguely):
· Intrinsic calibration: transforms image coordinates (i, j) into camera world coordinates (x, y) — correcting deformations from the optics and the camera's own properties (a real image never lands on a perfect rectangle; after correction the angular increment between neighbouring pixels is equal). Calibrated with a checkerboard (all square spacings equal and known). Concerns the camera itself only.
· Extrinsic calibration: transforms (x, y) into the local frame coordinates (X, Y) — it depends on how the camera is mounted in relation to the origin of the local frame; it is what lets you relate detections from various sensors to each other. Assuming a flat ground surface, a projective transformation can map every pixel to a ground-plane (X, Y). Vehicle frame convention: origin = centre of the first axle, X forward, Y to the left.
Exam point: what "relates the camera to other sensors" is the extrinsic calibration, not the intrinsic one.

HSV vs RGB (L5): HSV (hue–saturation–value) separates the image's intensity (luma) from its colour information (chroma) — colour becomes independent of brightness. So when lighting changes, colour filtering (e.g. "find the blue cone") stays stable; filtering colours directly in RGB is fragile because all three channels shift together with the lighting. (In OpenCV, H uses 0–180 instead of 0–360.)

§3 · Software engineering: Docker / microservices / CI-CD / OTA / git / deployment (★highest weight, 7 missed in June, L2/L3)

Principle (the full chain from one line of code to the robot): use git to version the source code (traceability) → CI (continuous integration) automatically builds and runs tests on every commit, producing a verified binary → (optionally with HIL testing on real hardware) → cross-compilation builds on an amd64 server a program the arm64 robot can run → packaged as a Docker container (docker run creates a container from an image; robots use the small Alpine base) → split into microservices that each handle a single task (sharing a common protocol, which helps OTA/CI-CD) → OTA (over-the-air updates) pushes software down to the robot; data flowing back up = remote monitoring.

Why containers are good (L2): a container is "operating-system-level virtualisation" — it shares the host kernel and isolates only the application environment, so it is far lighter than a virtual machine (each VM carries a whole OS + kernel). Three big wins: binaries live in a well-defined isolated environment; transferability between platforms; one self-contained bundle per software feature → naturally suited to OTA. The build chain benefits too: source code enters an isolated build environment, the build logic itself becomes portable, and cross-compilation tools can be installed (e.g. amd64 → arm).

The loop after shipping (L2): OTA serves not only products in the wild but also development — it brings the office closer to the physical product and provides version control for a whole fleet. Remote monitoring sends field data back to HQ, evaluated formally via KPIs (quantitative indicators defined for the whole robot fleet); KPIs are the enabler of CE (continuous experimentation). Typical CE move: release the new version to only a fraction (e.g. 20%) of users/robots first, and roll out fully only when the data proves it better — Tesla even ships features silently before public launch and observes them remotely in "what-if" mode, on roughly a million miles per day.

Which tool for parameter tuning (L5 — the principle behind Q31–33): each of the three options has a flaw — simulation: generally not reproducible, never realistic (motion and sensors), and computationally heavy (integrating dynamic equations); real hardware: not reproducible, large time overhead per test; data replay: open-loop → fully reproducible results; feed the same recording to the perception algorithm over and over to tune thresholds — the most efficient (one project's time split in the slides: 50% replay / 20% simulation / 30% hardware). But note: replay is open-loop — your control output cannot change the recording — so it cannot tune motion-control parameters (those need closed-loop feedback: simulation or hardware).

⚠️ Two counter-intuitive but officially settled points: microservices are about deployment/isolation/updates; choosing algorithms is a separate concern (hence "microservices make it easier to plan algorithms" is F in all three years); and differing CPU architectures (ARM↔AMD64) are routinely solved by cross-compilation (hence "the architecture difference is a general difficulty" is F).

§4 · Kinematics of the differentially steered robot (★the only derivation, L4)

Know the symbols first: r = wheel radius; R = distance from each wheel to the robot's centre (half the track width); L = distance from the ICR to the robot's centre; V = forward speed of the body; vL/vR = left/right wheel linear speeds; φ̇ ("phi-dot") = yaw rate, i.e. how fast the heading rotates.

Principle: different wheel speeds → the whole robot rotates about the instantaneous centre of rotation (ICR) with the same angular rate φ̇. With the ICR at distance L from the centre: vL = φ̇(L−R), vR = φ̇(L+R). Add → V = (vR+vL)/2 (no R!); subtract → φ̇ = (vR−vL)/(2R) (denominator 2R!). Solve back: vR = V + φ̇R.

Pose = integral of velocity (the complete L4 trio): decompose V into Vx = V·cosφ and Vy = V·sinφ, then integrate:
x₁ = x₀ + ∫ (vR+vL)/2 · cosφ dt　|　y₁ = y₀ + ∫ (vR+vL)/2 · sinφ dt　|　φ₁ = φ₀ + ∫ (vR−vL)/(2R) dt
x goes with cos, y goes with sin — a favourite swap trap. When a formula question appears, re-derive on scratch paper and check the coefficients.

Kinematics vs dynamics (needed again in §5): kinematics only answers "given the wheel speeds, how does the pose change" — it says nothing about how the motion is produced by forces. Dynamics considers the forces and torques acting on the robot (motor torque τ, mass M, moment of inertia I). Simulations use the dynamic model with Euler time-stepping (torques update V and φ̇ first, then φ, finally the position).

§5 · Kalman filter (★incl. the previously mis-judged Q47, L8)

Principle (following the KF notes): the Kalman filter formalises merging several data sources as mathematical expressions and is referred to as an optimal estimator. Every time step it runs two steps in a fixed order: ① Predict — use the process model to predict the current state from the previous one; ② Update — use the sensor readings (through the observation model) to estimate the prediction's offset and correct it. It is naturally good at handling data with different update frequencies (the model fills in while a sensor is silent) and at suppressing noise — hence "a KF is often used when sensors have too low update frequency / are noisy" are both T.

The two models, precisely (as in the notes): the process model describes "how the state transitions from one step to the next" (it can depend on process input; the notes explicitly name "the kinematics model of differential steering" as a good example). The observation model describes "how sensor readings correspond to the state variables" (it contains calibration data — scaling and bias removal). So "the two models are two ways of modelling the sensors" = F — the process model models motion.

Kalman gain: the noise itself is unpredictable, but it can be estimated as a trade-off between the previous estimate and the current observation — the gain is that weight (the notes: "the gain contains the system's trust for each observation"). It cannot increase sensor frequency (that benefit belongs to the filter as a whole, not the gain).

Online and recursive: the filter can run live throughout the robot's runtime, or on collected data — both work, so "a KF requires recorded data and cannot be used in a robot" = F.

Linearisation (the key exam point): the standard KF assumes both models are linear (only sums and proportionality between variables). When a model is non-linear, use the EKF: estimate the model's local derivatives around the current state using Jacobian matrices ("how does the model respond to small changes in the state?") and run the KF machinery on that local linear approximation. For the differentially steered robot: the kinematic relations between wheel speeds and V, φ̇ are linear → the standard KF works; but with the state vector [x, y, φ] the position update involves cosφ, sinφ ("curved" relations) → non-linear → EKF needed; the dynamic model (forces/torques) is likewise non-linear → EKF.

Where they are used (L8): sensor fusion — GNSS gives an occasional global reference (noisy, low-rate), wheel encoders/IMU track the movement between GNSS updates, and the internal (process) model removes noise; the KF merges all three. SLAM — drop GNSS too, and localise + map simultaneously from re-observed landmarks (in EKF-SLAM the state vector holds, besides [x,y,φ], each landmark's coordinates — size 3+2n, growing as landmarks are found; re-observing a landmark where it should be decreases the uncertainty).

§6 · Control / steering / PID + simulation + path planning (L6)

Lateral vs longitudinal (L6): longitudinal control = local speed adaptation along the X axis (forwards); lateral control = steering, staying on the path. Navigation splits into three concepts: localisation (find yourself in the map) → path planning (find an efficient path from there to the target — global) → path following (apply actuation to follow it — local).

Three steering models (all from research on how humans drive, starting with Kondo in the 1950s):
· Aim point model: fixate one point ahead; control law δ = k·ε (ε is the angular error towards the point) — only 1 tunable parameter, k.
· Preview model: take a series of preview points along the road ahead (the most famous model uses 8 points) → naturally more parameters. Hence "the aim point model has fewer parameters than the preview model" = T, and "the aim point model contains two tunable parameters" = F.
· Two-point model (Salvucci & Gray, 2004): mimics human gaze — the far point is a distant visual fixation (its position is situation-dependent) and serves to monitor lateral stability and predict steering for the upcoming curvature; the near point is the centre of the road just ahead, monitored peripherally (no fixation) for the current lateral position. The output is a steering rate: you move the wheel only when the near/far point moves in your view, or the near point is not straight ahead — the slides' punchline: steering is not about moving the vehicle, but about moving the perceived world.

PID and the rate limiter: the slides say "in most cases, a PID controller is perfectly fine". P corrects in proportion to the current error (the workhorse); I accumulates past error to remove steady-state offset; D damps according to the error's rate of change → resists oscillations. Steering relies on P and D — I is not the star. A rate limiter caps how fast the control output may change: vision-based perception is frame-by-frame and jumpy (detections flicker, positions jitter), and driving the steering directly from it makes the robot twitch — the rate limiter smooths the spikes.

Modular simulation (the L4 principle, one sentence): a microservice does not know where its data comes from — it only cares about message type and content — so any microservice can be swapped for a simulated counterpart (virtual camera, virtual wheel encoder, virtual vehicle... the same principle as data replay), and parts of the system can run simulated alongside physical parts. That is why it fits microservice architectures naturally and makes SIL/HIL easy. Contrast monolithic simulation (self-contained worlds like Gazebo, AirSim): you build a whole separate world and risk the "simulation rabbit hole" (endlessly optimising the simulation itself).

Path planning (L6): Dijkstra — starting from the start node, repeat two moves: relax all unvisited neighbours of the current node (if a shorter path is found, update its distance and record the predecessor), then pick the unvisited node with the smallest distance as the new current node; guarantees the shortest path but touches many nodes → basic, slow. A* = Dijkstra + a heuristic (an estimate of the remaining distance to the goal, so promising directions are explored first) → commonly used, quick. D* Lite suits real-world applications (incremental replanning as the environment changes). All of them find paths — none of them controls speed.

§7 · Decision making: FSM / BBR / Symbolic AI / evolutionary robotics / ANN (★3 missed in June, L7)

The three paradigms: Symbolic AI — centralised, functionally decomposed, with clearly defined data-processing stages (sense → model → plan → act): build a model of the world first, then reason and plan on the model. BBR — decentralised: a set of atomic behaviours (the smallest sense→act units, e.g. "avoid", "seek light") run in parallel (several can be active at once), and overall intelligence arises by emergence (complex whole-system behaviour that nobody programmed appears from simple interacting parts); the inspiration is ethology (animal behaviour), not human psychology. Behaviour selection/coordination is the central difficulty — the slides: "behavioural modelling comes down to coordination and tuning of simple isolated components" — hence "behaviour selection is trivial" = F. Evolutionary/embodied robotics (ER) — embodied intelligence argues intelligence can only be discussed relative to a physical body engaged in contextual behaviour; behaviours grow by evolution, with no predefined behaviours or data-processing stages.

FSM (the L7 definition): a graph of discrete logical states; each state = one concrete isolated behaviour (e.g. roaming, turning left); specific conditions (e.g. a stimulus above a threshold) trigger a transition to another state; the FSM imposes no hierarchy of behaviours. It can be implemented as if-statements acting on globally available variables. Its parameters (thresholds etc.) are set by hand — "an FSM automatically tunes its own parameters" = F.

Subsumption architecture (L7, per the slides): a reactive behaviour architecture — behaviours are ordered hierarchically; each behaviour has an activation criterion and is either active or inactive; behaviours run in parallel, but higher-order behaviours suppress the output of lower-level behaviours while active; modular: new behaviours can be added on top of existing ones (incremental design); tuning the activation criteria is crucial to the overall system behaviour. Each behaviour can internally be an FSM — the slides' example: the "Escape" behaviour = a 4-state FSM (waiting for a bumper hit → turning right → backing up → turning left, with transitions triggered by hit direction and timeouts) → hence "a subsumption architecture can be modelled from a set of FSMs" = T.

Braitenberg vehicles (1984): sensors wired directly to motors — the concept of a decision is reduced to a sensor→actuator mapping, and the mapping itself is the behaviour (no internal state, so "Braitenberg vehicles are implemented as FSMs" = F). In a complex environment with several stimulus sources they exhibit seemingly intelligent, complex, dynamic behaviour. The lesson, per Braitenberg's book: guessing the internal structure from observing behaviour is much harder than creating the structure that produces the behaviour — easy to build, hard to analyse; so "simple atomic behaviours result in easily explainable overall behaviours" = F.

How evolution "grows" behaviour (the L7 GA loop): generate a random initial population → decode each chromosome into a behavioural model → run and evaluate it in the actual environment → assign a fitness score → favour the fittest, apply crossover/mutation, produce the next generation. Strengths: handles non-differentiable objectives and problems without a complete mathematical model (e.g. evaluated in simulation or HIL); its parallel search copes with many local optima.

ANN (L7): a fully connected network is "a more general mapping between input and output", a blank-slate structure for behaviour — it can hold many parallel and blended behaviours at once; what you tune are each neuron's weights + bias (y = φ(w·x+b)), with an activation function (e.g. sigmoid) keeping inputs/outputs within [0, 1]. A sufficiently large fully connected ANN can achieve any input→output mapping (universal approximation) — T on the exam.

§8 · A short history of robots (★2 missed in June, L1)

The four pioneers (L1, detailed):
· The Tortoise (W. Grey Walter, 1948–49): the first electronic autonomous robots. Their very purpose was to prove that rich connections between a small number of "brain cells" could give rise to very complex behaviours — emergence. Capable of phototaxis: they could find their way to a recharging station when low on battery. Built entirely with analogue circuits — the microcontroller was invented in 1971, 23 years later, so "the Tortoise is famous for being first with a microcontroller" = F.
· The Stanford Cart (1960–80, three phases): 1960–63, research on video-based teleoperation for remote moon missions; 1964–71, automatically following a high-contrast white line at slow speed under controlled lighting; 1971–80, visual navigation with a TV camera, slowly steering around obstacles in a lab.
· Shakey (Stanford Research Institute, Nils Nilsson et al., 1966–72): the first general-purpose mobile robot able to reason about its own actions; it could also process natural language — breaking written commands down into basic tasks. Huge impact on robotics and AI: the A* search algorithm and the Hough transform both came out of this project. Like the Kiwi, it is a wheeled mobile robot carrying a camera and distance sensors (26 Q2, "clear physical similarities" = T).
· Braitenberg vehicles (1984, Valentino Braitenberg's book): sensors wired straight to motors; simple structure, complex behaviour (see §7).

Hype vs what actually shipped (the L1 timeline): 80s personal companion robot hype → 90s deep-neural-network hype + personal work robot hype → 00s first humanoid hype (ASIMO wowed the public; later evolving into more useful things like Boston Dynamics' dog) → 10s autonomous cars + machine-learning hype → 20s the LLM "AI" hype + a second humanoid hype. What actually succeeded commercially were modest products solving real problems: Husqvarna's robotic lawn mowers and iRobot's Roomba — so "personal robots really took off in the 90s" = F (it was hype only).

Appendix · 30-minute pre-exam review (ordered by past mistakes)

  1. The software-engineering chain (most mistakes): git versions source code, binary traceability comes from CI-CD; CI includes automated testing; HIL can join automated testing; cross-compilation = crossing CPU architectures (amd64→arm64), routine work; docker run creates a container, use small Alpine; microservices share a protocol, help OTA-CICD, and are about deployment/isolation ("planning algorithms" is F all three years); OTA = pushing software down (data coming back = monitoring).
  2. Computing hardware: PLD = reconfigurable circuitry, fastest | microcontroller = bare metal → real-time | CPU = OS multitasking but poor real-time | GPU = matrices/vision.
  3. Kinematics: V=(vR+vL)/2 (no R), φ̇=(vR−vL)/2R (denominator 2R), position = integral of velocity; vR=V+φ̇R.
  4. Kalman: Predict then Update; process = motion, observation = sensors; gain = trust weight, not frequency; kinematic model linear → standard KF works; [x,y,φ] with φ / dynamic model non-linear → EKF.
  5. Decision making: Symbolic AI has stages | BBR: parallel, emergent, from ethology, selection non-trivial, buildable from FSMs/subsumption, Braitenberg hard to explain | ER: no predefined stages | large ANN = universal approximator.
  6. Control: two-point model = near + far point, output is a rate; D damps; rate limiter smooths vision; aim point has fewer parameters (not two); modular simulation fits microservices, makes SIL easier.
  7. Sensors: ultrasonic outranges IR; Bayer = most green; rolling shutter is faster; intrinsic = the camera itself, extrinsic = links to other sensors.

Glossary of abbreviations (look things up here)

Each entry = abbreviation | full name (the memory anchor) | what it actually is, in one line. Abbreviations are hard to remember when you only memorise three letters — read the full name a few times and the abbreviation starts meaning something.

Computing hardware

PLD | Programmable Logic Device
A chip that can be reconfigured into any special-purpose circuit (it is hardware circuitry, often mistaken for a small computer). Extremely fast and power-efficient.
FPGA | Field-Programmable Gate Array
A kind of PLD; "gate array" = a large field of logic gates you wire as you like. Treat as a synonym of PLD here.
CPU | Central Processing Unit
The general-purpose brain that runs an operating system; manages many programs at once, but with poor real-time guarantees.
GPU | Graphics Processing Unit
Specialised in massively parallel matrix operations; excels at vision and neural networks.
MCU | Microcontroller Unit
A whole "computer" shrunk onto one small chip (CPU + memory + I/O integrated), dedicated to controlling one device. On power-up it runs a fixed program directly on bare hardware (i.e. "no OS"); predictable behaviour → real-time capable.
OS | Operating System
System software that manages hardware and schedules many programs (e.g. Linux); it constantly interrupts/switches programs for fairness — great for multitasking, but "when is my turn" becomes uncertain → hard real-time is difficult.
real-time
Guaranteed completion within a set deadline (punctual, predictable). An OS-less microcontroller can be real-time; an OS-based CPU can hardly guarantee it. (Real-time = on time, not "fast".)
ROM / RAM | Read-Only / Random-Access Memory
ROM holds the fixed program (survives power-off); RAM is the temporary working memory (lost at power-off).

Sensors & cameras

IR | Infrared (distance sensor)
Emits infrared light and measures the reflection. Course unit: Sharp GP2Y0A41SK0F — range only 4–30 cm, analogue voltage output, non-linear in distance. Minimum range above zero.
Ultrasonic (distance sensor)
Emits 40 kHz sound pulses and times the echo. Course unit: Devantech SRF08 — range 3 cm–6 m (far longer than IR), built-in microprocessor, I²C interface.
RGB | Red-Green-Blue
The three primary colour channels. The sensor produces colour via the Bayer filter array (2×2 = 2 green, 1 red, 1 blue).
ISP | Image Signal Processing
The processing that turns raw Bayer patterns into normal RGB images: demosaicing (Bayer→RGB), white balancing, gamma correction, tone mapping, noise reduction. Vision algorithms almost always use post-ISP data.
rolling / global shutter
Rolling: rows exposed and read one by one (each row a slightly different moment) → cheap, fast, skews motion. Global: all pixels exposed at the same instant, then read out together → no distortion, but more expensive and slower.
HSV | Hue-Saturation-Value
A colour representation separating intensity (luma) from colour (chroma) — colour independent of brightness, so colour filtering stays stable under lighting changes; much handier than RGB.

Software engineering (the second-weakest block — read carefully)

Docker | containerisation tool
Packs a program together with all its dependencies into one "shipping container" that runs identically on any machine — the cure for "works on my machine".
image vs container
An image is a packaged static template (like an install disc); a container is a running instance of the image (like the installed, running system). docker run = create and start a container from an image; docker build is what makes images.
Alpine / Ubuntu | two Linux distributions
Common Docker base images: Ubuntu is big and full-featured; Alpine is minimal (tiny). Robots want small → Alpine.
multi-stage build
One Dockerfile with two FROMs — the first stage (builder) installs the build tools and compiles; the second copies over only the compiled program. Result: a final image containing just the program → very small (the build tools stay behind in the builder stage). (This is exactly what the 24/25 Dockerfile figure questions test.)
microservice
Splitting one big program into many independent small programs, each handling a single task, developed/deployed/replaced individually and communicating via a common message protocol. (Opposite = monolithic: welded into one block.)
technical debt
The "debt" incurred by taking shortcuts — convenient now, repaid later with interest (refactoring, bug fixing).
CI | Continuous Integration
Owns the "build + test" stage — every commit triggers an automatic build and test run, ensuring new and old code fit together. Output: a tested binary.
CD | Continuous Deployment
Owns the "release" stage — automatically deploys the CI-produced, test-passing binary to the product (the robot).
CI/CD in one line
CI comes first and produces a verified binary; CD comes after and delivers it to the robot automatically. Together = a fully automatic pipeline from commit to deployment.
CE | Continuous Experimentation
After release, ship to only part of the fleet first (canary/gradual rollout) and evaluate with data before going wide.
OTA | Over-The-Air (update)
Remotely delivering/installing new software onto robots in the field — the direction is software going down. (Contrast: software down = OTA; data coming back = remote monitoring.)
HIL | Hardware-In-the-Loop
Wiring real hardware into the test loop; can be automated.
SIL | Software-In-the-Loop
Running the real code entirely inside a software simulation (hardware replaced by simulation).
Data replay
Replaying previously recorded real data for testing — open-loop, fully reproducible.
Memory chain: SIL (pure software) → HIL (real hardware attached) → data replay (recorded data fed in) — all are testing/verification means, increasingly close to reality.
KPI | Key Performance Indicator
A quantitative measure of how well robots perform in the field.
SSH | Secure Shell
The tool for logging in remotely and typing commands on the robot (that is its actual job).
UDP | User Datagram Protocol
A fast "send and don't wait for receipts" network transport; libcluon uses its multicast to pass messages between microservices.
ROS | Robot Operating System
A large but monolithic robot software framework — appears in the course as the contrast to OpenDLV.
OpenDLV
The robot software environment used in this course: a loose collection of libcluon microservices (lighter and more modular than ROS).
ARM64 / AMD64
Two CPU instruction-set architectures. Memory hook: small power-efficient devices use ARM64 (Raspberry Pi / robots), big powerful servers use AMD64/x86 (GitLab CI); different architectures → cross-compilation (routine work, not a "difficulty").

Kinematics & state estimation

ICR | Instantaneous Centre of Rotation
The point the whole vehicle rotates about at a given instant — the starting point of the kinematics derivation.
KF | Kalman Filter
The optimal estimator that formalises merging several data sources: each step predicts with a model, then corrects with measurements. Linear models only (non-linear → EKF).
EKF | Extended Kalman Filter
The non-linear version of the KF — local linearisation via Jacobian matrices; required for the differentially steered robot whenever cos/sin φ appears.
SLAM | Simultaneous Localisation And Mapping
The robot estimates its own position and builds the map at the same time as it moves.
GNSS | Global Navigation Satellite System
The umbrella term for satellite positioning (GPS is one of them); provides a global reference, but noisy and low-rate.
IMU | Inertial Measurement Unit
Measures accelerations and angular velocities; used for dead reckoning.

Control & decision making

PID | Proportional-Integral-Derivative (controller)
The classic three-term controller. P does the main correction, I removes steady-state error, D resists oscillations.
FSM | Finite-State Machine
Behaviour-switching logic built from "in this state, when a condition holds, jump to that state"; can be implemented as if-statements acting on global variables.
BBR | Behaviour-Based Robotics
The paradigm of many simple behaviours running in parallel with intelligence emerging as a whole; inspired by ethology.
ER | Evolutionary Robotics
The paradigm of evolving controllers with evolutionary algorithms; behaviour grows naturally (no predefined stages).
Symbolic AI
The traditional paradigm: model first, then plan; staged and centralised.
ANN | Artificial Neural Network
A sufficiently large fully connected net is a "universal approximator" that can fit any mapping.
GA | Genetic Algorithm
Random population → fitness-based selection → crossover + mutation → next generation; the usual tool of evolutionary robotics.
A* / Dijkstra / RRT (Rapidly-exploring Random Tree)
Path-planning algorithms; A* = Dijkstra + a heuristic.
